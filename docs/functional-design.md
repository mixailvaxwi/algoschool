# AlgoSchool — проектирование функциональности

Документ описывает целевую функциональность платформы: акторов, доменные объекты,
полный перечень сценариев использования, изменения в модели данных и порядок
реализации.

Отправная точка — то, что уже работает: курсы из модулей, уроков и шагов; шаги
четырёх типов (теория, код, текстовый ответ, выбор варианта); запись на курс
самостоятельно или по заявке; отправка решений с проверкой кода в Ejudge;
бинарный прогресс по шагу. Всё остальное ниже — надстройка над этим, а не замена.

---

## 1. Акторы

| Актор | Кто это | Как получает роль |
|---|---|---|
| **Гость** | Неавторизованный посетитель | — |
| **Студент** | Учится и решает задачи | Роль по умолчанию при регистрации |
| **Преподаватель (автор)** | Владелец курса: содержание, состав, оценки | Назначает администратор |
| **Соавтор** | Правит содержание чужого курса | Приглашает автор курса |
| **Ассистент (TA)** | Проверяет решения, отвечает на вопросы, не правит курс | Назначает автор курса |
| **Администратор** | Пользователи, роли, модерация, системные настройки | Выдаётся в базе / другим администратором |
| **Система** | Фоновые процессы: опрос вердиктов, дедлайны, рассылки, агрегаты | — |

**Ключевое изменение в модели прав.** Сейчас роль глобальна (`users.role`), и
`/api/teacher/**` открыт любому `ROLE_TEACHER`, а принадлежность курса
проверяется отдельно в `CourseAccessService`. Соавтор и ассистент — это роли
*внутри курса*, глобальной ролью они не выражаются. Нужна таблица членства:

```
course_members(course_id, user_id, role)   role ∈ {OWNER, COAUTHOR, ASSISTANT, STUDENT}
```

Глобальная роль остаётся как грубый фильтр маршрутов, точные права — из членства.
`CourseAccessService` остаётся единственным местом проверки — расширяется, не
дублируется.

## 2. Доменные объекты

### 2.1 Что есть сейчас

```
Course ──< Module ──< Lesson ──< Step
                                 ├── TheoryStep      (content)
                                 └── Problem         (description, счётчики)
                                     ├── CodeProblem   (лимиты, ejudge ids)
                                     ├── TextProblem   (correctAnswer)
                                     └── ChoiceProblem (options, correctOptionIndex)

UserCourse (запись), CourseApplication (заявка),
Submission (попытка + вердикт), UserStepProgress (бинарный прогресс)
```

### 2.2 Что нужно добавить

Главная проблема: `Problem extends Step`, то есть **задача физически принадлежит
одному уроку**. Одну и ту же задачу нельзя поставить в два урока или в два курса
— только скопировать. А копия расходится с оригиналом при правке условия, и
статистика (`attempted_students_count`, `success_students_count`) размазывается
по копиям, из-за чего сложность задачи перестаёт быть измеримой.

**Решение: разделить «задачу» и «размещение задачи».**

```
Problem  — единица содержания и оценивания, живёт в банке задач
├── id, authorId, title, description, tags[], difficulty, maxScore, visibility
└── подтипы (JOINED, как сейчас):
    CodeProblem, ChoiceProblem, TextProblem,
    NumericProblem, MatchingProblem, OrderingProblem, OpenAnswerProblem

Step — размещение содержания в уроке
├── TheoryStep   (content)
└── ProblemStep  (problem_id)   ← вместо Problem extends Step
```

Новые сущности:

| Сущность | Назначение |
|---|---|
| `Problem` | Задача в банке: переиспользуется в разных уроках и курсах |
| `Group` / `GroupMember` | Поток/группа внутри курса |
| `Deadline` | Срок на урок или задачу, опционально для группы |
| `Grade` / `GradeItem` | Журнал: оценка за элемент, формула итоговой |
| `Notification` | Уведомление в интерфейсе + канал доставки |
| `AuditEvent` | Кто что изменил (роли, оценки, ререйдж) |

`Submission` расширяется баллами и полями ручной проверки — сейчас там только
вердикт:

```
Submission += score, max_score                  — баллы, а не только «решено/нет»
           += reviewed_by, review_comment       — для развёрнутых ответов
```

## 4. Оценивание и прогресс

### 4.1 Что не так сейчас

`UserStepProgress.isCompleted` — булев флаг, `Submission` не хранит баллов.
Пока задача либо решена, либо нет, невозможны: частичные баллы за подзадачу,
вес задачи в курсе, журнал оценок. Баллы нужно хранить на уровне отправки.

### 4.2 Модель баллов

```
Submission.score / max_score      — за конкретную отправку
Grade(user, grade_item)           — зачтённый балл за элемент по политике
GradeItem                         — задача урока | ручная оценка,
                                    с весом в итоговой оценке
```

Политика зачёта задаётся на уровне элемента: лучшая попытка, последняя, первая,
средняя.

### 4.3 Критерий завершения курса

Настраивается автором, варианты:

- доля пройденных шагов ≥ X %;
- все обязательные шаги пройдены;
- итоговый балл по формуле ≥ порога;
- комбинация условий.

Итоговая оценка = взвешенная сумма по группам элементов (теория, задачи) с
настраиваемыми весами и возможностью отбросить N худших результатов.

## 5. Изменения в API

Существующие маршруты не ломаются; добавляются новые разделы.

```
# Банк задач
GET    /api/teacher/problems?tag=&difficulty=&q=
POST   /api/teacher/problems
PUT    /api/teacher/problems/{id}
POST   /api/teacher/problems/{id}/rejudge

# Проверка и оценки
GET    /api/teacher/submissions?courseId=&problemId=&userId=&status=
GET    /api/teacher/review-queue                # развёрнутые ответы на проверку
POST   /api/teacher/submissions/{id}/grade      # балл + комментарий
GET    /api/teacher/courses/{id}/gradebook
GET    /api/teacher/courses/{id}/gradebook/export
GET    /api/courses/{id}/my-grades

# Группы и дедлайны
POST   /api/teacher/courses/{id}/groups
PUT    /api/teacher/courses/{id}/deadlines
POST   /api/teacher/courses/{id}/members        # соавтор, ассистент

# Потоковые обновления
GET    /api/submissions/stream                  # SSE: готовые вердикты

# Администрирование
GET    /api/admin/users?q=
PUT    /api/admin/users/{id}/role
POST   /api/admin/users/{id}/block
GET    /api/admin/queue                         # зависшие PENDING
GET    /api/admin/audit
```

Правила, обязательные для новых маршрутов:

- **Время задаёт сервер.** Клиент не присылает время сдачи или наступления дедлайна.
- **Ограничение частоты** на отправку решений — по пользователю и по задаче.
- **Ответы и тесты не покидают сервер.**
- Единый формат ошибок сохраняется (`ErrorResponse`).
- Для доступа к сессиям и отзыву входов нужны refresh-токены: сейчас JWT
  самодостаточен и отозвать его нельзя.

## 6. Миграция модели

Разделение `Problem` и `Step` — самое дорогое изменение. Порядок:

1. **V5** — создать `problems` и подтипы, перенести строки из `step_problems` и
   его подтаблиц, проставить `author_id` из автора курса.
2. **V6** — создать `problem_steps(step_id, problem_id)`, для каждой перенесённой
   задачи создать размещение в её уроке.
3. **V7** — перевести `submissions.problem_id` и `user_step_progress` на новые
   идентификаторы, сохранив соответствие; добавить `score` / `max_score`.
4. **V8** — `course_members`, `groups`, `deadlines`, `grade_items`, `grades`.
5. Старые таблицы удаляются отдельной миграцией через релиз, когда код перестал
   к ним обращаться.

Каждая миграция — как `V2`: сначала разрешение конфликтов данных, потом
ограничения. Hibernate остаётся в режиме `validate`.

## 7. Нефункциональные требования

| Тема | Требование |
|---|---|
| Время | Единственный источник — сервер; все дедлайны в UTC, отображение в часовом поясе пользователя |
| Параллелизм | Фоновые задачи под ShedLock: опрос вердиктов уже сейчас не защищён от второго экземпляра |
| Реальное время | SSE вместо поллинга для готовых вердиктов |
| Устойчивость | Недоступность Ejudge не теряет отправку: очередь и ретраи |
| Честность | Ограничение частоты, лимит попыток, антиплагиат |
| Приватность | Чужие решения недоступны студенту; развёрнутые ответы видит только проверяющий |
| Аудит | Смена ролей, оценок, ререйдж — с автором и причиной |
| Доступность | Плеер проходится с клавиатуры |
| Данные | Экспорт своих данных и обезличивание при удалении аккаунта |
