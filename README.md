# AlgoSchool

Платформа для курсов по программированию: преподаватель собирает курс из модулей,
уроков и шагов, студент проходит их в плеере. Задачи на код проверяются внешней
системой [Ejudge](https://ejudge.ru/), текстовые и тестовые — самой платформой.

**Стек:** Spring Boot 3.5 / Java 21 / MySQL / Flyway · React 19 / TypeScript / Vite / Zustand

---

## Быстрый старт

### 1. Переменные окружения

```bash
cp .env.example .env
```

Заполните обязательные значения:

| Переменная    | Обязательна | Описание                                                    |
|---------------|-------------|-------------------------------------------------------------|
| `DB_PASSWORD` | да          | Пароль пользователя MySQL                                    |
| `JWT_SECRET`  | да          | Ключ подписи токенов, Base64, минимум 32 байта               |
| `DB_URL`      | нет         | По умолчанию `jdbc:mysql://localhost:3306/algoschool?...`     |
| `DB_USERNAME` | нет         | По умолчанию `root`                                          |

Ключ подписи генерируется так:

```bash
openssl rand -base64 32
```

Без `JWT_SECRET` приложение осознанно **не стартует** — вместо того чтобы молча
подписывать токены значением из репозитория.

### 2. Запуск

Через Docker (поднимает MySQL, бэкенд и дев-сервер фронтенда):

```bash
docker compose up --build
```

**IntelliJ IDEA.** Переменные из `.env` среда запуска не читает — их нужно задать
в конфигурации: `Run` → `Edit Configurations` → поле `Environment variables`,
значения через точку с запятой:

```
JWT_SECRET=<ключ из openssl rand -base64 32>;DB_PASSWORD=<пароль MySQL>
```

Если переменные не заданы, приложение не стартует и печатает список
недостающих — это ожидаемое поведение, а не поломка.

Или вручную из терминала — MySQL уже запущена, база `algoschool` создана:

```bash
set -a && . ./.env && set +a && ./mvnw spring-boot:run
```

```bash
cd algoschool-frontend && npm install && npm run dev
```

Фронтенд поднимется на `http://localhost:5173`, бэкенд — на `http://localhost:8080`.

### 3. Первый администратор

Регистрация всегда создаёт студента: роль не принимается от клиента, иначе любой
желающий сделал бы себя администратором. Самому первому администратору права
выдаются напрямую в базе — дальше роли выдаются через панель администратора
(`/admin/users`, доступна пользователю с `ROLE_ADMIN`):

```bash
mysql -u root -p algoschool -e "UPDATE users SET role='ROLE_ADMIN' WHERE username='<логин>';"
```

## Переменные окружения Ejudge

Проверка задач на код требует запущенного Ejudge. Без него платформа работает,
но такие задачи будут получать статус `SUBMISSION_FAILED`.

| Переменная               | По умолчанию       | Описание                                       |
|--------------------------|--------------------|------------------------------------------------|
| `EJUDGE_BASE_URL`        | `http://localhost` | Адрес Ejudge                                    |
| `EJUDGE_API_KEY`         | пусто              | Ключ master API                                 |
| `EJUDGE_BOT_LOGIN`       | `ejudge`           | Логин, от имени которого отправляются решения   |
| `EJUDGE_POLLING_ENABLED` | `true`             | Опрос вердиктов; выключите, если Ejudge не поднят |

Сопоставление языков с `lang_id` зависит от конкретной установки Ejudge и
задаётся в `application.yml` (`ejudge.language-ids`).

## Схема базы

Схемой управляет Flyway (`src/main/resources/db/migration`), Hibernate работает в
режиме `validate` и схему не меняет. Миграции накатываются при старте приложения.

Для баз, созданных до подключения Flyway, включён `baseline-on-migrate`: `V1`
помечается применённой без выполнения, изменения приезжают начиная с `V2`.

> `V2` перед созданием уникальных ограничений удаляет накопившиеся дубликаты
> записей на курсы, заявок и прогресса. Прочитайте её, прежде чем запускать на
> базе с реальными данными.

> `V7` разделяет задачу и её размещение в уроке: переименовывает `step_problems`
> в `problems`, снимает внешний ключ на `steps` и заводит `problem_steps`.
> Строки не копируются, идентификаторы сохраняются, но откатить её штатными
> средствами нельзя — сделайте дамп перед запуском на реальных данных.

## Тесты

```bash
./mvnw verify                 # модульные и срезовые — без инфраструктуры
./mvnw verify -Pintegration   # плюс подъём контекста, нужна живая MySQL
```

Интеграционные тесты помечены `@Tag("integration")` и по умолчанию
пропускаются. В CI их выполняет отдельная задача с сервисом MySQL.

Покрыто: проверяющие модули шагов, разбор вердиктов Ejudge, подпись и разбор JWT,
правила доступа к курсу и матрица доступа на уровне маршрутов.

## Структура

```
src/main/java/com/algoschool/
├── auth/          регистрация, вход, выдача JWT
├── user/          профили пользователей
├── admin/         пользователи, роли, блокировка, сброс пароля
├── course/        курсы, модули, уроки, записи и заявки
│   └── service/CourseAccessService — единственное место проверки прав на курс
├── problem/       банк задач: условие, ответ, теги, статистика (наследование JOINED)
├── step/          шаги урока: теория и размещение задачи из банка
├── submission/    решения, прогресс, проверяющие модули
├── ejudge/        клиент внешней проверяющей системы и опрос вердиктов
├── config/        безопасность, JWT, обработчики 401/403
└── exception/     AppException и единый формат ошибок
```

**Задача и шаг — разные вещи.** `Problem` живёт в банке и не знает ни про урок,
ни про курс; `ProblemStep` — это её размещение в конкретном уроке. Одну задачу
можно поставить в несколько уроков: правка условия меняет её везде сразу,
а счётчики попыток и решений остаются общими. Снятие шага убирает размещение,
но не задачу.

Ответы об ошибках всегда имеют вид:

```json
{ "status": 404, "error": "Not Found", "message": "Курс не найден", "timestamp": "..." }
```

## Известные ограничения

- **`npm run lint`** выдаёт около 30 накопившихся ошибок и поэтому не включён в CI.
- Задача в банке видна либо только автору, либо всем преподавателям: промежуточной
  видимости «участникам курса» нет, пока у курса нет соавторов и ассистентов.
- Пересчёт уже выставленных вердиктов после правки задачи (ререйдж) не реализован.
- Прогресс по-прежнему бинарный: `maxScore` у задачи хранится, но в баллы не превращается.
- Редактирование и удаление модулей, уроков и шагов после создания не реализовано.
